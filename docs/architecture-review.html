3. 关键机制（读代码归纳）

一视图一 YGNode，没有渲染树

View 持有 YGNode*，通过 YGNodeSetContext 反查 View*；布局靠 Yoga 递归，绘制靠 View::frame 递归，两者共用同一棵树。 这是 borealis 的核心选择，bklv 完整保留 —— 好处是不存在“布局树与渲染树不同步”这类 bug，代价是 View 必须同时承载布局、外观、焦点、手势、动作、变换、属性表七类职责。

延迟布局，一帧最多一次

invalidate() 只冒泡置脏，真正的 YGNodeCalculateLayout 在 App::frame 里按三条件触发（首帧 / 画布尺寸变 / 有人置脏）。 静态页面布局次数为 0/帧。BKLV_FORCE_RELAYOUT=1 可退回每帧全量以排查漏置脏。

四级注册表（真正的扩展机制）

  • 图层类型 compile::registerLayer() —— parse + draw 双钩子，设计器菜单自动跟随
  • 视图类型 registerViewType() —— compile 注册内置，widgets/widget_types.cpp 注册控件，App::App() 调一次
  • 数据源 data::registerSource()、绑定器 binding::registerItemBinder()

全部显式注册、重名报错、拒绝静态初始化魔法，且有实物证据：demo/contrib/stripe_layer.cpp 仅新增一个文件就加出了 "op": "stripe" 图层。

外观 JSON 驱动的样式系统

控件在 C++ 里只写行为与结构，尺寸/颜色/圆角/状态动效/转场全部来自主题 JSON；代码里显式设过的值不可被主题覆盖（explicit 标志）。 四类 JSON（视图描述 / 控件外观 / 主题 / 文案）都有完整键表文档 docs/json-syntax.md（35 KB）。

构建中后端归属不可见 bklv/CMakeLists.txt:324-327 把 gl_glass.cpp / vk_glass.cpp 等 4 个后端专属文件无条件编进 BKLV_CORE_SOURCES（GL 构建下 vk_glass.cpp 整体被 #if 包住 = 空 TU）；Switch 脚本又要手列一遍（scripts/build_switch.sh:144-146）。另：GLES3 的玻璃复用的是桌面 GL 的实现，其中 READ/DRAW framebuffer 绑定语义在 ES3 里本不保证，Switch 能编过是因为 devkitPro 的 GLES3/gl3.h 恰好定义了那几个枚举。 “一个后端一个构建目录”的约定在源码清单这一层看不出来；GLES3 那条属于依赖工具链巧合，换工具链或升级头文件就会断。

4.4 对 demo 与 designer 的评价

demo —— 合格的“能力总览”，但承担了部分库职责

结构清晰：demo_app.cpp 负责外壳组装（Shell 四层 + Pager 懒加载 + Sidebar 导航 + Header/BottomBar），页面由 Pager::setPageFactory 注册成工厂（切页现建、旧页现删，见 demo/app/pages.hpp:1-13），pages/ 每页一个 .cpp（共 15 页），ui.cpp 是排版小工具（makeText/makeHint/…），contrib/ 放第三方扩展样例（stripe_layer.cpp）。main.cpp 只有 44 行，是很好的接入示范。 Tab 导航（TabFrame/TabCell）本身是库里的控件，demo 只在导航页与基础控件页演示它 —— 这一点分层是干净的。

问题：页头/底栏的折叠补间留在 demo（demo/app/demo_app.cpp:343-351 的 headerAnim/footerAnim + 逐帧 App::requestLayout()），AGENTS.md 明确写“库侧不再提供”——这是有意决定，但结果是任何想复现“顶栏可折叠外壳”的项目都必须抄这段代码。建议把“外壳栏折叠动画 + 内容避让”收进库（Shell 已经有 insets 接口，缺的只是补间），demo 只留装配。

designer —— 定位正确，但体量失衡

分层是对的：designer/core/（逻辑层，不含界面代码，可由 tests/designer_core_test.cpp 无窗口测）+ ui/（ImGui 面板）+ glass/ + mockup/。用 ImGui 做编辑器界面、用 bklv 真实视图做预览，是这类工具的正确技术选型（编辑器 UI 与产品 UI 需求完全不同）。

问题：ui/designer_window.cpp 6117 行 / 77 个方法 / 977 处 ImGui:: 调用 / 头文件 234 个成员，占设计器代码 53%；其中 5 个函数就占 41%（drawProps 724 行、drawModals 644、drawPreview 428、draw() 348、drawTree 347）。它是标准的 God Object，且 ui/ 层零测试（designer_core_test.cpp 只覆盖 core/ 的 16 个文件）。逻辑/界面分层已经做对了，下一步应按面板拆文件（属性检查器 / 预览 / 文件树 / 弹窗），否则这个文件会持续吸引“顺手加一个按钮”的改动。

另外两点：designer/main.cpp 里有约 30 处 getenv 自查开关（:44-243）—— 与项目“demo 里不要加环境变量调试开关”的约定方向相反，虽在 designer 上仍属同一条理由；mockup/index.html 是 HTML 样板房、不进构建，不会造成污染。demo 与 designer 零互相 include，两端都只依赖库，这条边界是干净的。

5. 附录 · 证据与复现方式

本文所有依赖边与规模数字由只读脚本得出，可复现：

  • 目录规模：find bklv/<dir> -name '*.cpp' -o -name '*.hpp' | wc -l，行数用 wc -l 求和
  • 依赖边：解析 #include "bklv/..."，按 bklv/<子目录> 归并成 dir→dir 计数（结果见 §2.1 表）
  • 抽象穿刺：grep -rn '#include "bklv/\(backends\|platforms\|widgets\|compile\)' bklv/core bklv/glass
  • ImGui 全局调用：grep -rn 'ImGui::' bklv/core bklv/views（合计 6 处非 app.cpp 调用点）
  • 单例：grep -rn '^ static \|^ static ' bklv/core/*.cpp bklv/views/*.cpp bklv/widgets/*.cpp
  • 头文件级环检测：对 102 个 bklv/**.hpp 建 include 图做 DFS 染色 → 无跨模块环（详见 §2.1）
  • 后端能力矩阵：grep -n 'readPixels\|updateTexture' bklv/backends/*.cpp → 仅 opengl_backend.cpp:107 覆盖 readPixels
  • 公开头污染链：grep -n 'glass_service.hpp\|shell.hpp' bklv/bklv.hpp + grep -n 'vulkan.h' bklv/backends/vk_glass.hpp
  • RTTI：grep -rn 'dynamic_cast\|typeid' bklv demo designer → 只在注释里出现，实现零使用（Switch -fno-rtti 约束被遵守）
